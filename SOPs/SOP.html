01System overview

Facebook, Instagram and the website all feed one AI agent (workflow 1), which qualifies the lead and writes it into HubSpot. From there: booking confirmations and reminders (workflow 2), a nurture drip for cold leads (workflow 3), and review requests or recovery follow-ups once a job is won or lost (workflow 4). Telegram and WhatsApp nodes exist in workflow 1 but are currently unregistered — safe to leave idle until those channels are turned on.

Full visual diagram: Documentation/workflow-diagram.html. One-time setup steps: Documentation/build-guide.html. This document is the ongoing operations manual — what to do after setup, not instead of it.

03Daily checklist

  • n8n → Executions: any failed runs (red)? Open one, note which node failed, check §5.
  • HubSpot → Deals: any "Qualified – Ready to Book" sitting untouched? A human should be moving these to a booked call within the day.
  • Telegram ops group: any escalation alerts sitting unanswered?
  • Spot-check one AI conversation from the last 24h (HubSpot contact → notes) — is the tone and qualification logic still on-brand and accurate?

04Weekly / monthly checklist

  • Weekly: review nurture-drip conversions — how many cold leads moved to booked this week?
  • Weekly: confirm workflow 4 actually sent review requests for jobs marked Won, and recovery messages for Lost/no-shows.
  • Monthly: check AI API usage/billing (Anthropic/Google AI Studio/xAI consoles) against expected volume — a spike often means a loop or malformed trigger, not more leads.
  • Monthly: check Twilio balance and delivery logs for SMS fallback failures.
  • Every January: STC rebate figures step down — update STC_MESSAGE in n8n `.env` and the pricing figures on the website (see §4 of the pricing reference in workflow-diagram.html).
  • Monthly: HubSpot Free contact count — approaching 1,000 marketing contacts means it's time to plan the upgrade, not discover it mid-campaign.

05Troubleshooting

Website form/chat isn't creating HubSpot leads
Usually one of: webhook URL still the placeholder, workflow not Active, or CORS blocked in the browser.
Fix: Open admin.html, unlock it (see Documentation/settings-access-guide.md), then Test connection. A CORS failure message specifically points at the "Website Inbound" node's Allowed Origins setting in n8n.
AI replies are generic, wrong, or ignore known lead info
System prompt not reflecting current service area/pricing, or the wrong AI provider is active without its key configured (silently falling back to a generic error reply).
Fix: Check "Build AI Request" node output in the failed Execution — confirm provider matches what you expect and its API key exists in .env.
Reminders (24h/1h) never fire
Deal's appointment_datetime property never got set, or workflow 2 isn't Active.
Fix: Confirm the HubSpot Meeting actually created a Deal association, and that workflow 2's "Find New Meetings" search window (last 20 minutes) isn't being missed by a slow booking sync.
Review requests or recovery follow-ups not sending
Deal stage ID in .env doesn't exactly match HubSpot's actual internal stage ID (labels can look identical while the internal ID differs).
Fix: HubSpot API → GET /crm/v3/pipelines/deals → confirm HUBSPOT_STAGE_WON / HUBSPOT_STAGE_LOST match exactly.
Facebook/Instagram messages never reach the AI agent
Page Access Token expired (short-lived tokens expire — use a long-lived or System User token), or the Instagram account isn't actually linked to the same Page as the app.
Fix: Re-generate the token in Meta's dashboard, confirm IG Business account link under Page settings, re-save in n8n .env.
Can't log into admin.html — browser's login popup rejects correct-looking credentials
Almost always a mismatch between what's typed into the Vercel/Netlify Environment Variables form and what's typed into the browser prompt — commonly the username ends up typed into the variable's Key field instead of its Value field. Once a variable is marked "Sensitive," its value can't be read back to check — not even via vercel env pull.
Fix: Don't try to guess what's wrong. Remove both variables (vercel env rm ADMIN_BASIC_AUTH_USER production, repeat for _PASS and the preview environment) and re-add them fresh, then redeploy. See Documentation/deploy-lockdown-guide.md for the exact commands.

06Change procedures

Update pricing

  1. Edit the Pricing section directly in solterra-landing-au-solarfirst.html.
  2. If the AI should quote these numbers in conversation, also update the "Build AI Request" node's system prompt in n8n.

Add a team member to escalation alerts

  1. Add them to the Telegram ops group directly — no code change needed, the alert already targets the whole group via TELEGRAM_OPS_CHAT_ID.

Switch the default AI provider

  1. Confirm the target provider's API key is set in n8n .env.
  2. Change AI_PROVIDER_DEFAULT for all non-website channels, or change it per-visitor via the website's own Integration Settings.

Rotate a leaked or expiring API key

  1. Generate the new key at the provider (don't delete the old one until the new one's confirmed working).
  2. Update the value in n8n .env, save/restart n8n if your host requires it for env changes to take effect.
  3. Run one test message through that specific channel, confirm it in n8n Executions, then revoke the old key.

Rotate the admin.html host-level lockdown credentials

  1. Hosting dashboard → Environment Variables → remove ADMIN_BASIC_AUTH_USER / ADMIN_BASIC_AUTH_PASS (or edit their values in place, if the platform allows it).
  2. Add the new values, applied to Production (and Preview, if used).
  3. Redeploy — env var changes only take effect on a fresh deployment.
  4. Confirm from outside before relying on it: curl -o /dev/null -w "%{http_code}" https://your-domain/admin.html should return 401 with no credentials, 200 with -u user:pass.

Reskin the whole site for a new client

See website/REBRAND-GUIDE.md — a 5-step, ~15-minute process.

07Incident response

IncidentImmediate action
n8n instance is downAll channels stop responding silently (leads still land in Meta/website but get no reply). Restart n8n; check Telegram/Meta webhooks re-verify automatically once it's back — if not, re-save the webhook URL at the provider to force re-verification.
HubSpot free-tier limit hit (contacts, emails)New contacts stop syncing correctly. Short-term: prioritise upgrading or archiving stale contacts. This is a "plan ahead" item, not a same-day fix — see §4 monthly check.
Unexpected AI API cost spikeCheck n8n Executions for a runaway loop (e.g. a webhook re-triggering itself) before assuming it's just lead volume. Pause the workflow if costs are climbing faster than lead volume explains.
A channel's webhook stops verifyingUsually a verify-token mismatch after a token was regenerated. Re-check META_VERIFY_TOKEN / WHATSAPP_VERIFY_TOKEN match exactly between n8n .env and the provider's dashboard.

09Known limitations

Documented on purpose, not hidden. These are the gaps between "logic verified" and "production-hardened."

  • No live end-to-end test yet. The n8n workflows have been verified by simulating their code with mocked inputs (Node.js), not by actually running in n8n against real provider traffic. Run the full test table in build-guide.html §12 before relying on this for real leads.
  • No automatic retry on API failures. If HubSpot, Anthropic, or any other call fails mid-execution, n8n stops that run — the lead is silently dropped rather than retried. Recommended before full production use: add "Continue on Fail" + a dedicated error-handling workflow that alerts the Telegram ops group on any failed execution.
  • No deduplication for duplicate webhook deliveries. Meta and WhatsApp can occasionally redeliver the same webhook event; the workflow currently has no idempotency check, so a rare duplicate could create a second contact or send a duplicate reply.
  • No monitoring beyond the hot-lead Telegram alert. A silent failure in qualification or a stalled drip wouldn't page anyone — the daily checklist in §3 is currently the only safety net.
  • Single point of failure. Everything routes through one n8n instance with no documented backup/failover.
Recommendation: treat §3's daily checklist as mandatory, not optional, until the retry/monitoring gaps above are closed — it's currently doing the job that automated alerting should be doing.
